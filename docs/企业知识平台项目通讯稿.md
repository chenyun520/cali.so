# 企业知识平台项目通讯稿：结构分析与维护说明

分析日期：2026-09-09。范围：博客主应用、导航与项目展示链路、关联的数据与布局依赖，以及本次新增专题。不是整站安全审计或业务系统验收报告。

## 博客结构与本次切入点

| 层次 | 现有实现 | 对本次工作的影响 |
| --- | --- | --- |
| 应用框架 | Next.js App Router、React、TypeScript；锁文件安装结果为 Next 14.2.35 / React 18.3.1 | 复用现有路由与组件，不创建第二个生产应用 |
| 页面外壳 | 根布局加载 Clerk、字体、主题；`app/(main)/layout.tsx` 组合 Header、内容区、Footer | 专题继承原博客外壳、浅深色主题与响应式容器 |
| 导航配置 | `config/nav.ts` 由电脑菜单、手机菜单、页脚共同使用，已有 `/projects` | 不重复增加“项目”菜单，补充子路径的选中状态 |
| 内容管理 | Sanity 管理博客、项目引用、履历和首页图片；查询在 `sanity/queries.ts` | 此次固定排版的通讯稿保存在代码中，不要求先调整 CMS 模型 |
| 项目列表 | `/projects` 读取 settings 的 projects；`Projects` 默认只展示前三项 | 新专题独立置顶，原项目保留在下方；项目总览传入完整数量 |
| 原有项目卡片 | `ProjectCard` 采用外链按钮，按 URL 或名称识别汇报材料；首页另用 `HomeProjectList` | 不把长文硬塞进外链模型，不修改原项目访问行为；本次入口位于项目菜单页 |
| 互动服务 | Clerk 登录；Neon + Drizzle 支持留言、评论与订阅；Redis 支持计数与互动；Resend 负责邮件 | 专题正文没有新增数据库、登录、写接口或邮件依赖 |
| 公开访问 | `middleware.ts` 显式列举公开路由 | 单独加入新专题地址，避免访客被引导登录 |
| 收录 | 路由 Metadata 与 `app/sitemap.ts` | 补充文章标题、简介、canonical、分享图片及 sitemap |

现有 `/projects` 的角色是作品索引，博客文章的角色是 CMS 内容阅读。此次采用“作品索引中的精选专题 → 站内通讯稿”，既保持项目归属，也允许专题采用独立的编辑式版面。全文使用服务端组件和局部 CSS，没有为文章另加动画库、富文本编辑器或客户端数据请求。

## 内容与设计

- 标题：让经验有处可寻，让知识有序流动。
- 主线：现场问题 → 查找资料 → 沉淀经验 → 审核与版本 → 长期管理。
- 形式：项目通讯稿，不是产品登录入口，也不是逐项操作说明。
- 视觉：暖白、深绿与陶土橙，宋体强调句，编号章节，宽幅界面图，双栏叙事与审核流程示意。
- 阅读：五个章节锚点、返回项目、点击界面图在新标签页查看原尺寸；手机采用单列及两列流程图。
- 边界：没有写入平台访问凭据，没有连接本地业务系统的公开按钮，没有虚构用户数、上线规模或节省工时。

## 已识别的既有维护点

1. 整站本地运行需配置 `.env.example` 中的外部服务；Footer 直接查询订阅数据库，阅读页也受共享布局的数据依赖影响。
2. `next-sanity` 的已安装版本声明 Next 15/16 的 peer dependency，而主应用使用 Next 14。此次没有升级框架；后续应独立规划版本兼容核验。
3. 根 Metadata、`lib/seo.ts`、`lib/index.ts` 中有分散的站点地址与继承内容，后续宜根据正式域名集中整理。本次专题使用相对 canonical 和图片地址，沿用主站配置。
4. 通讯稿目前随代码更新；如果以后持续发布大量项目纪实，再为 Sanity 增加明确的站内项目内容类型，比继续按外链或名称判断更易维护。
